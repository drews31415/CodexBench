## 1. 배경

원 기준에서 Main 편입에는 BQ01–14 전체가 필요하다. 이 중 BQ14는 작성자가 아닌 리뷰어의 승인이다(BENCHMARK_SPEC §11.1, G2_PREPARATION의 비작성자 검토 절차). 2026-11-27 기준 상황은 다음과 같다.

- 후보 8개 모두 큐레이터 Docker 평가(기준본 기능 FAIL·회귀 PASS, 참조본 전체 PASS) 통과가 보고됐다.
- BQ14를 수행할 사람 리뷰어가 없다. 운영자는 앞으로도 사람을 포함하지 않기로 결정했다.
- 그래서 승인된 Main 과제가 0개이고 G2를 통과할 수 없다(IMPLEMENTATION_PLAN §10.1).

이 수정안은 **BQ14를 사전 고정한 독립 AI 리뷰와 강화된 객관적 검사로 대체**하는 규칙을 Main 결과를 보기 전에 등록한다. 수정된 기준을 충족해도 원 기준(사람 동료 리뷰)을 충족했다고 표기하지 않는다.

## 3. 바꾸지 않는 것 (불변)

- A–E 조건 정의와 resolver, 정책 격리, B/D·C/E byte parity (AGENTS §5.1)
- 그래프·감지·전략·DCC 정책, 가중치·임계값(METHODOLOGY §15 시작값). Pilot 결과를 보고 조정하지 않는다
- 모델과 런타임: `gpt-6-luna`, low, Codex CLI 0.166.0, 기존 ChatGPT 구독 인증
- 슬롯별 한도: Pilot 값 그대로. 실행 360초, B–E 복구 최대 2회, 전이 100, cleanup 15초, 보조 컨텍스트 2,048 추정 토큰, 토큰 `observe_only`
- 격리: Windows MXC 권한 프로필 `aah_dev01_mxc`, 개발 세션의 비공개 검사 비접근, 독립 평가 프로세스 분리
- 독립 판정 규칙(기능·회귀·필수 제약), 세 가지 상태 분리, 미실행 슬롯을 분모에 보존
- 분석 원칙: 완전 블록, task family cluster bootstrap 10,000회, seed 20261126, 95% percentile, CPS 무정의 replicate가 있으면 구간 보류

## 4. BQ14 대체: 독립 AI 리뷰

### 4.1 독립성 요건

| 요건 | 내용 | 기록 |
| --- | --- | --- |
| 별도 세션 | 과제 작성 세션, 개발 세션과 다른 **새 세션** | 세션 시작 시각, 도구 이름 |
| 작업 위치 | 큐레이터 키트 폴더 안에서만 실행. 저장소의 개발 이력·대화·Pilot 결과를 입력하지 않음 | 작업 디렉터리 |
| 계정 분리 | 실험 대상인 Codex/ChatGPT 계정으로 리뷰하지 않음. 비공개 검사가 실험 대상 계정의 이력에 남지 않게 하기 위해서다 | 사용한 제공자 |
| 모델 | 가능하면 비공개 검사를 작성한 모델과 다른 계열. 같은 계열이면 그 사실을 기록 | 모델 ID |
| 고정 지침 | 개발 세션이 미리 작성해 SHA-256을 고정한 리뷰 지침만 사용. 추가 질의·유도 금지 | 지침 해시 |

### 4.2 리뷰 입력과 출력

- **입력:** `task.json`, `baseline/`, `reference/`, `curator_tests/`, §5의 객관적 검사 보고서, BQ01–14 기준 원문
- **출력:** 과제별 리뷰 기록 JSON
  - 포함 항목: 리뷰 모델 ID, 지침 해시, 과제 ID, BQ01·04·05·06·11 판정과 근거, 최종 판정(`APPROVE`/`HOLD`)
  - BQ04·06의 근거에는 비공개 검사 하나하나가 공개 명세의 어느 문장에서 나왔는지 인용해야 한다
  - 리뷰 기록 파일의 SHA-256을 **검토 증거 ID**로 사용하고, 리뷰어 ID는 `ai-review:<모델 ID>`로 쓴다
- **연구 저장소로 전달하는 것:** 과제 ID, 리뷰어 ID, 검토 증거 ID, 항목별 판정만. 비공개 검사 내용은 넘기지 않는다

### 4.3 판정 규칙

리뷰 결과가 `APPROVE`이고 §5의 모든 객관적 기준이 통과해야 BQ14 대체 기준 충족이다. `HOLD`이면 그 과제는 편입하지 않는다. 리뷰 결과로 다른 과제의 판정을 바꾸지 않는다.

## 5. 객관적 검사 기준 (과제별)

대안 구현과 불완전 수정본은 **개발 세션이 공개 명세(`task.json`, 공개 기준본, 공개 검사)만 보고** 작성한다. 개발 세션은 비공개 검사를 볼 수 없으므로, 대안 구현이 비공개 검사를 통과하는지는 테스트가 숨은 요구를 하는지에 대한 독립적인 증거가 된다. 비공개 검사 판정은 운영자가 키트 폴더에서 명령으로 실행한다.

| BQ | 기준 | 통과 조건 |
| --- | --- | --- |
| BQ01 요구사항 | 공개 명세에 재현 조건·기대 동작·제약이 있음 | AI 리뷰 판정 |
| BQ02·03 기준본/참조본 | 큐레이터 Docker 평가 | 기준본 기능 FAIL·회귀 PASS, 참조본 기능·회귀·지시 PASS |
| BQ04·06 테스트 타당성·대안 구현 | 서로 다른 접근의 대안 구현 **2개 이상**(공개 검사 통과본만) | 대안 구현이 비공개 검사를 **모두 통과**. 실패한 경우는 AI 리뷰가 실패 검사를 공개 명세 문장으로 정당화할 때만 허용(대안 구현 쪽 오류). 정당화하지 못하면 FAIL |
| BQ05 불완전 수정 | 그럴듯한 부분 수정본 **3개 이상** | 비공개 검사가 **1개 이상** 검출. 검출률도 보고 |
| BQ07 공개 검사 | 고정 Docker 공개 검사 실행기 | 기준본 결과가 2회 동일하고 파싱 오류 없음 |
| BQ08 반복 안정성 | 기준본·참조본 각각 2회 이상 | 같은 입력·환경에서 결과 일치 |
| BQ09·10 격리·동등성 | MXC 접근 검사(`access_check`)를 과제별 A–E 수행 | BQ09·BQ10 모두 PASS. 비공개 합성 파일 접근 0건 |
| BQ11 문서 상태 | NORMAL/NOISY/STALE과 보관 문서의 역할 표기 | AI 리뷰 판정 |
| BQ12 분리·중복 | 후보 간, Dev 과제와의 family·upstream 중복 | 8개 family가 서로 다르고 Dev family와 겹치지 않음(레지스트리 대조) |
| BQ13 권리·운영 | 자체 작성 과제, 고정 Docker 이미지 | 외부 라이선스 의존 없음, 이미지 ID 기록 |

**검사 수정 허용 범위:** BQ04·05·06에서 실패한 과제는 **Main 동결 전에 한 번** 비공개 검사를 고칠 수 있다. 고친 뒤에는 BQ02–10 전체를 다시 확인한다. 두 번째 실패는 `HOLD`다. 모든 수정은 이유와 함께 기록한다.

## 6. 편입과 최소 규모

- 대상: 후보 8개(AAH-S02, S03, D02, D04, R03, R04, C02, C03)
- **최소 편입 수 5개.** 승인 과제가 5개 이상이면 Main을 실행하고, 4개 이하면 Main을 실행하지 않는다. 그 경우 사유와 과제별 BQ 결과만 보고한다
- 편입·제외는 Main 첫 슬롯 실행 **전에** 확정한다. 실행 뒤 결과를 보고 과제를 빼거나 더하지 않는다
- 과제 무효가 실행 중 발견되면 그 과제의 모든 조건에 같이 적용한다(EXPERIMENT_DESIGN §12.4)

## 7. 실행 범위와 예산

### 7.1 Protocol 1 — End-to-end (필수)

| 항목 | 값 |
| --- | --- |
| 슬롯 | 편입 과제 수 × A–E × 1회(최대 40) |
| 순서 | `runner.plan`, seed 20261127. 과제 정렬 후 과제마다 조건 순서를 섞음 |
| 턴 상한 | 최초 1턴 × 슬롯 + B–E 복구 2턴 × B–E 슬롯. 8과제면 **최대 104턴** |
| 비용 | 기존 구독, **추가 결제 0원**. 토큰은 관측만 함 |
| 추정 사용량 | Pilot 평균 기준 약 370만 토큰, 예비 20% 포함 약 440만. 상한이 아니라 추정치 |
| 중단 규칙 | 계정 사용 한도 도달 시 남은 슬롯은 `NOT_RUN_BUDGET`. 재실행·선택 폐기 금지. 안전·격리 위반 시 즉시 중단 |

### 7.2 Protocol 2 — 공통 실패 체크포인트 (조건부)

다음 **세 가지를 모두** 만족할 때만 실행한다. 하나라도 빠지면 P-R2를 `NOT_RUN`과 사유로 보고한다.

1. 라이브 체크포인트 경로를 구현하고 합성 검증한다. 내용은 source 실행이 첫 적격 trigger에서 멈추고, snapshot을 복원하고, B–E를 `NEW_SESSION`으로 분기하는 것이다. 검증은 Main 동결 전에 끝나야 한다
2. 별도 실험 ID와 별도 승인이 있어야 한다. 예산은 source 최대 8턴 + 분기 최대 32회(분기당 복구 2턴, 최대 64턴)다
3. E2E 실행이 먼저 끝나야 한다

Pilot에서 B 첫 턴의 공개 검사 실패가 0/5였으므로 적격 체크포인트가 0건일 수 있다. 그 경우에도 시도 수와 비용을 보고하며, 0건은 "측정 불가"이지 "효과 없음"이 아니다.

### 7.3 Protocol 3 — Ablation

수행하지 않는다. AB1–AB4는 `NOT_RUN`(Emergency 생략)으로 기록하고, 구성 요소별 효과를 주장하지 않는다.

## 9. 승인 구조

1. 운영자가 이 수정안을 승인하면 DL-031을 `APPROVED`로 바꾸고 승인자와 일자를 기록한다. 1인이 RH·GR·CE를 겸임한다고 명시한다
2. 동결 manifest(`aah-main-emergency-v1`)에 이 수정안 파일의 SHA-256을 기록한다
3. 실행 승인 파일에는 다음을 적는다: 동결 manifest의 SHA-256, 예산 재기재(§7.1), 과제별 리뷰어 ID·검토 증거 ID(§4.2), 세 역할 승인자, 수정안 해시
4. 실행 게이트는 과제별로 둘 중 하나를 확인한다: 레지스트리 `APPROVED` + 사람 리뷰, 또는 `AMD01_APPROVED` + AI 리뷰 기록 해시. 수정안을 거친 과제는 레지스트리에 `AMD01_APPROVED`로 따로 표시하고 `APPROVED`로 쓰지 않는다

## 11. 한계 (승인 전 확인)

1. **상관 오류:** 과제 작성, 대안 구현, 리뷰, 실행이 모두 AI다. 같은 방향의 명세 해석 오류를 서로 잡지 못할 수 있다
2. **1인 승인:** 역할 분리에 의한 상호 견제가 없다
3. **Pilot 결과 열람 후 등록:** Dev 결과를 본 뒤 작성했지만 정책과 지표는 바꾸지 않았다. 바꾼 것은 리뷰 절차와 규모뿐이다
4. **규모:** 과제 최대 8개, 반복 1회, 저장소 3개라서 구간이 넓고 저장소 상관을 통제하기 어렵다
